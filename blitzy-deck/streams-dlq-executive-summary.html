Opt-In Dead Letter Queue for the Kafka Streams DSL

Capture and route failed records — no lost data, no stopped threads.

Executive Summary
Section

01

What We Built & Why

The Capability

A DSL-level DLQ, opt-in per stream

  • New DSL method KStream.withDeadLetterQueue(...)
  • Failed records are routed to a configured DLQ topic
  • Added as a Java default method — fully backward compatible
  • Reuses the existing Streams producer
Business Value

Resilience without disruption

  • No stopped stream threads on one bad record
  • No silent data loss
  • Full diagnostics via record headers
  • Zero impact on healthy traffic

Threads keep running

DLQ-eligible failures are captured and processing resumes — no fail-fast stop.

No silent loss

Eligible failures are routed to the DLQ topic instead of being skipped.

Failure-path only

DLQ logic runs on the exception branch; the healthy record path is untouched.

After

Opt-in layer routes failures to the DLQ

flowchart TD
    accTitle: Error-Handling Data Flow — After (opt-in DLQ layer)
    accDescr: When a stream has the DLQ active — either through the withDeadLetterQueue DSL call or the global default.deadletterqueue.enabled switch — a failed record is passed to the DLQ-aware decorator, which delegates to the configured handler and routes only DLQ-eligible failures. It resolves the effective topic, builds the dlq.* record, sends it through the shared producer, increments the metric and logs a WARN, then resumes. Topologies without the DLQ active follow the unchanged legacy path.

Diagnostics

Every DLQ record carries six headers

dlq.exception.class dlq.exception.message dlq.source.topic dlq.source.partition dlq.source.offset dlq.failure.timestamp

Original key and value bytes are preserved via a passthrough serializer.

Configuration

One clear precedence order

Most specific withDeadLetterQueue(...) Per-stream DSL call — wins whenever present
Fallback Global defaults default.deadletterqueue.* — applied when no DSL call is made
default.deadletterqueue.topic default.deadletterqueue.enabled  =  false
Observability

Measure and alert on dead-letters

  • New metric dlq-records-sent-total, tagged by thread and task
  • WARN log on each DLQ write (exception class + source offset)
  • Alert on DLQ growth

Adoption, Risks & Next Steps

Risks & Mitigations

Known trade-offs, handled

Best-effort delivery

Same producer; under exactly-once, written inside the task transaction. A failed DLQ write escalates once — monitor the metric.

DLQ topic must pre-exist

Provision it via standard admin tooling before enabling.

Oversized record

Truncate-and-annotate — the record is never dropped.

Naming coexistence

New dlq.* scheme coexists with the legacy KIP-1034 path.

Safety

Nothing changes unless you opt in

  • Non-DLQ topologies byte-for-byte identical
  • Public interfaces unchanged (wrapped, not modified)
  • Same producer, same security/auth — no new credential surface
  • DLQ logic confined to the failure branch

Opt-in by design: the healthy record path is untouched.
