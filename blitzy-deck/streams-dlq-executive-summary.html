Capture and route failed records — no silent data loss, no stopped threads.

01

What We Built & Why

The Capability

A DSL-level DLQ, opt-in per stream

  • New DSL method KStream.withDeadLetterQueue(...)
  • Failed records are routed to a configured DLQ topic
  • Added as a Java default method — fully backward compatible
  • Reuses the existing Streams producer
Business Value

Resilience without disruption

  • No stopped threads on a bad record
  • No silent data loss
  • Full diagnostics via record headers
  • Zero impact on healthy traffic

Threads keep running

Failures are captured; processing resumes.

No silent loss

Routed to the DLQ, not skipped.

Failure-path only

Healthy path untouched.

After

Opt-in layer routes failures to the DLQ

flowchart TD
    accTitle: Error-Handling Data Flow — After (opt-in DLQ layer)
    accDescr: When a stream has the DLQ active — either through the withDeadLetterQueue DSL call or the global default.deadletterqueue.enabled switch — a failed, DLQ-eligible record is passed to the DLQ-aware decorator, which delegates to the configured handler. A WARN is logged for the routing attempt (exception class and source offset), the effective topic is resolved (the DSL value overrides the global default), DlqRecordBuilder builds the dlq.* record (truncating and annotating an oversized value rather than dropping it), and RecordCollector sends it through the shared producer; processing then resumes immediately. The dlq-records-sent-total counter is incremented only once the broker acknowledges the DLQ record. Topologies without the DLQ active follow the unchanged legacy path.

Diagnostics

Six diagnostic headers — on by default

dlq.exception.class dlq.exception.message dlq.source.topic dlq.source.partition dlq.source.offset dlq.failure.timestamp

Original key and value bytes are preserved via a passthrough serializer. Headers are on by default (and can be disabled); a truncated value adds two annotation headers.

Adoption, Risks & Next Steps

Risks & Mitigations

Known trade-offs, handled

Best-effort delivery

Same producer; under exactly-once, within the task transaction. A failed write escalates once — monitor the metric.

DLQ topic must pre-exist

Provision it via standard admin tooling before enabling.

Oversized record

Truncate-and-annotate — the record is never dropped.

Naming coexistence

New dlq.* scheme coexists with the legacy KIP-1034 path.

Safety

Nothing changes unless you opt in

  • Non-DLQ topologies byte-for-byte identical
  • Existing signatures preserved — one additive default method
  • Same producer, same security/auth — no new credential surface
  • DLQ logic confined to the failure branch

Opt-in by design: the healthy record path is untouched.
